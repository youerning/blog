# 内网穿透工具实测 · 结果汇总

> 实测时间：2026-11-21 22:50–23:30（北京时间）
> 两台真机：阿里云广东 `203.0.113.10`（server 侧）、UCloud 香港 `203.0.113.20`（client 侧 + 被测服务）
> 被测服务：香港机上的 iperf3（:61000）+ 一个返回 200 字节的 HTTP 服务（:60990）
> 探测端：广东机（同机打本地映射端口 / 直连打香港公网 IP）
> 原始数据：`raw/<tool>/`，汇总：`results.csv`，图表：`figs/`

## 先叠个甲（方法说明）

这篇不是 star 排行榜，是「同一件事用不同工具做，代价差多少」。有几个前提必须先讲清楚，否则数字会被误读：

1. **跨境链路本身是天花板**：广东→香港直连单流约 **7.8 Mbps**（4 流反而降到 7.2，说明是**单流约 7.8 Mbps 的限速**，多流能叠到 ~15）。所有隧道的吞吐对比都顶在这条天花板上，中继式之间拉不开差距——这是链路的属性，不是工具的属性。
2. **延迟用 TTFB 替代握手延迟**：隧道里 TCP 握手在本地就完成了，测握手没有意义，所以统一量 HTTP 首字节时间（curl `time_starttransfer`），每工具 20 次取 p50/p95。
3. **每项 3 次取中位**，文里不写单一数字假装精确；failures 如实记录。
4. **nps 有历史 RCE + 停更 1.5 年**，只在测试期开、用高端口 + 随机口令，测完即停。
5. 云防火墙只放行 22 + 60000–61000，这直接决定了 bore 的失败（见下）。

## 关键结论（写文章的骨架）

1. **中继式之间性能差异很小，都可忽略**。常态 TTFB 都在 **9–35ms**，单流吞吐都顶到链路天花板上（6.9–7.5 Mbps）。对个人用途，「选哪个更快」是个伪问题。

2. **真正的分水岭是「要不要自己的公网机器」**：
   - 中继式（frp/rathole/nps/chisel/bore）：要一台公网 VPS，换来的是**稳定 + 快 + 完全可控**。
   - 边缘托管（cloudflared/localtunnel）：一台机器都不用，代价是**国内出口体验差**——cloudflared 免费 quick tunnel 首字节 1.1 秒、p95 近 3 秒，是直连的 **50 倍**；localtunnel 的公共服务端在国内/香港直接连不上。

3. **资源占用有量级差**：rathole 9.1MB < chisel 13.7MB < nps 21.8MB < frp 27MB。在 2C2G 小机器上，rathole 省下的内存不是数字游戏。

4. **nps 是最典型的「榜单陷阱」**：34k star、常年霸榜各种「2026 推荐」，但**最后提交停在 2024-05-30，停更约 1.5 年**，且有历史 RCE。它本次功能上能用（23.9ms / 7.06Mbps），但「能用」和「该用」是两回事——这是文章最值钱的一段。

5. **失败项本身就是结论**：
   - bore：一条命令的极简设计，代价是控制端口写死 7835，在只放行特定段的云主机上直接不可用；
   - localtunnel：依赖公共服务器，服务器连不上时你毫无办法；
   - cloudflared：「免费无限」「不用服务器」是真的，但「国内快」是假的。

6. **单流 7.8 / 多流 15 的限速规律**：单条 TCP 被限到约 7.8Mbps，开 4 流能叠到约 15（rathole 14.99）。这条对「大文件传输要不要多线程」有直接指导意义。

## 三类东西不该放一张表里比

文章会保留一节专门讲这个（对应原 PLAN 去掉 Tailscale/EasyTier 的决定）：

| 类别 | 本质 | 要不要自己的公网机器 | 代表 |
|---|---|---|---|
| A. 中继式 | 公网跑 server，内网跑 client，流量全过中继 | **要** | frp、nps、rathole、chisel、bore、sish |
| B. 边缘托管 | 用厂商全球边缘节点当中继 | 不要（但要能连到厂商） | cloudflared、localtunnel |
| C. 组网式 | 不是映射端口，是把设备拉进同一个虚拟局域网 | 不要（要协调服务器/账号） | Tailscale、ZeroTier、EasyTier |

把它们混在一起比 star 没有意义：frp 110k 星不代表比 cloudflared「好用」，它们解决的问题不一样。
